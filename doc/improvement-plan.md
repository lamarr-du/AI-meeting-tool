# meetmin 改进规划

本文汇总对 AI 会议纪要工具（meetmin）尚未完成的改进点，按功能类别和优先级归纳（已对照源码核验完成的条目已移出）。每个改进点包含问题、改进思路，以及完成该改动所需的难度值（1–9 分制，换算规则见第 0 节）。

- 依据：通读全部源码；用一段 5 分钟、4 人发言的真实会议录音实跑到转写为止（未调用大模型）。
- 初次评估环境：Linux、4 核 CPU、15 GB 内存、无 GPU。当时录音模块和 CUDA 路径无法运行；后续 Windows 实测和实现进展记录在各条目中，不能再将所有录音结论视为未经验证。

## 0. 阅读说明

### 证据标记

| 标记 | 含义 |
|---|---|
| 【实测】 | 用示例音频或离线测试实际跑出来的结果 |
| 【读码】 | 从源码直接能确认的问题 |
| 【推断】 | 根据代码和经验判断，尚未实际验证 |

### 优先级

| 级别 | 含义 |
|---|---|
| P0 | 阻断：装不上、跑不通、丢数据。不修则工具基本不可用 |
| P1 | 明显影响转写/纪要质量或日常使用 |
| P2 | 工程质量与进阶体验 |
| P3 | 远期能力 |

### 难度换算规则

每条末尾的「难度」是经验判断，不是硬性要求，按 1–9 分制，由「任务复杂度档位」决定主区间、「投入强度」决定区间内取值：

- **复杂度档位**：
  - 改动位置明确、几乎没有设计空间的机械修改（改版本号、改文案、加一个参数）→ 低档，难度 **1–3**；
  - 范围清晰的单模块功能，有明确验收标准，能配单元测试 → 中档，难度 **4–6**；
  - 涉及并发、算法选型、跨模块重构，或需要自己设计实验来判断好坏的任务 → 高档，难度 **7–9**。

例如：机械修改 + 少量权衡 = 难度 2；单模块功能 + 中等权衡 = 难度 5；跨模块重构 + 需排查隐蔽问题 = 难度 9。

两条通用提醒：

1. 录音相关改动（B 类）需要可访问真实 WASAPI 设备的 Windows 环境。云端离线测试不能替代实机验收；在具备设备访问能力的本地环境中可直接运行验收脚本，并记录设备、场景与结果。
2. 转写、分离、术语相关改动（C、D、E 类）应先建好基准集（D6），让 AI 用指标说话。

## 1. 实测结论摘要

### 1.1 术语识别（已按你确认的原词校正）

确认的原词：demosaic、bypass、white level、constrain、@、默认、统计值、workaround；模块名 DRCST 读作 DRC Stat。

各配置下的识别情况（人工比对，✓ 正确，△ 接近，✗ 错误）：

| 原词 | small 默认 | small + 热词 | turbo 默认 | turbo + 提示语 |
|---|---|---|---|---|
| demosaic | ✗ 迪马斯克 | ✗ 迪马森克 | ✗ 迪马赛克 | ✗ 迪马赛克 |
| bypass | ✗ 拍片/拍不上/单拍不 | ✗ 拍摄上 | ✗ PiPlan/type | ✗ pipel/type/单拍不 |
| white level | ✗ 外他 level | ✗ 外特来往 | ✗ Wet Level | ✓ |
| constrain | ✗ 坑寸 | ✗ 坑寸 | ✗ 坑村 | △ kontrains |
| @ | ✗ 爱他 | ✗ 爱他 | ✗ 爱他 | ✓ at |
| 默认 | ✗ 摸着 | ✗ 摸着 | ✓ | ✓ |
| 统计值 | ✗ 统计师 | ✗ 统计制 | ✓ | ✓ |
| workaround | ✗ walk around | ✓ | 该段丢失 | ✓ |
| DRC Stat | ✗ drcstd | ✗ DRC STD | △ DRCState | △ drcstata/drcstates |
| 缩略词大小写 | 全小写 | ✓ 大写 | ✓ 大写 | 全小写 |

（small = faster-whisper small；turbo = large-v3-turbo；均为 CPU int8。）

结论：

1. **默认的 small 模型对中英混杂的技术会议不够用**：10 类里几乎全错，且没有标点。
2. **large-v3-turbo 的中文明显更好**，但默认解码不稳定：无提示时丢了约 50 秒内容，结尾出现幻觉文本；加热词后出现循环重复和整段英文幻觉。
3. **demosaic 和 bypass 在所有配置下都没被识别出来**。这类"被听成中文谐音"的词不能指望识别模型，必须有转写后的纠错层。
4. **错误的术语表会污染结果**：我在实验里把模块名误写成 `DRC STD` 放进热词，模型就照着输出 `DRC STD`；不加该热词时 turbo 反而输出更接近正确的 `DRCState`。术语入库必须经人确认。
5. 人名同样不稳定：同一个人在不同配置下被写成三种不同的字，人名也应进术语表。

### 1.2 解码稳定性补充实验

拿到你确认的术语后，我补跑了一组实验：large-v3-turbo，关闭"以前文为条件"（`condition_on_previous_text=False`），术语表改用正确写法。

| 配置 | 内容完整性 | 标点 | 术语 |
|---|---|---|---|
| turbo，关闭前文条件，无提示 | 完整，无重复，无幻觉 | 无 | `DRC` 多处变成 `DIC`；其余与默认相近 |
| turbo，关闭前文条件，术语句放进 `hotwords` | 完整，无重复，无幻觉 | 有 | @、默认、patch、white level、workaround、DRC Stat 均正确 |

第二种配置是目前所有实验里最好的一组。它仍然存在的错误：

- demosaic 仍是"迪马赛克"，bypass 仍是"type 上 / 单拍不 / PypLot"；
- constrain 被写成了 `conference`。这是一个看起来通顺的错词，比乱码更危险，纪要模型很可能照单全收；
- `DRC Stat` 偶尔写成 `DRC States`。

由此得到三条可以直接落地的结论：

1. **关闭"以前文为条件"应成为默认**。它消除了内容丢失、循环重复和幻觉。
2. **术语提示应走 `hotwords` 而不是 `initial_prompt`**。关闭前文条件后，`initial_prompt` 只对第一个 30 秒窗口生效，`hotwords` 则对每个窗口都生效；把一句带标点的中文术语句放进 `hotwords`，同时解决了标点问题。
3. **谐音类错误仍需转写后纠错**（D3、D4），识别前提示解决不了。

说明：这组实验只在 turbo 上跑完，small 模型在同样设置下的表现尚未验证；结论基于单段 5 分钟音频，需要用基准集（D6）复核。

### 1.3 说话人分离（实际为 4 人）

| 配置 | 结果 |
|---|---|
| 原样代码，默认配置 | 进程被系统因内存不足杀死，无任何产物 |
| 修复输入形状并分批，默认阈值 0.55 | 50 个簇，44 个说话人 |
| 阈值 0.7 / 0.8 / 0.9（窗长 1.5 秒） | 11 人 / 5 人 / 2 人 |
| 阈值 0.7 / 0.8（窗长 3 秒） | 5 人 / 1 人 |
| 指定 4 人（窗长 1.5 秒） | 输出 5 人，其中两人占了 251 秒里的 247 秒，其余三人各 1–2 秒 |
| 指定 4 人（窗长 3 秒） | 输出 4 人，时长为 179 / 69 / 2 / 0 秒 |

结论：

1. **即使告诉它正确人数，也分不出 4 个人**，实际只分出两个大簇，剩余名额被零星的异常窗口占掉。问题不在阈值，而在"短窗嵌入加平均链接层次聚类"这个做法对异常窗口没有抵抗力。
2. 阈值没有稳妥的默认值，换一个窗长最优阈值就变了。
3. 修复后 5 分钟音频的分离耗时约 46 秒、峰值内存 1.8 GB（CPU）。

### 1.4 性能参考（4 核 CPU，int8）

| 模型 | 5 分钟音频耗时 | 折算 1 小时会议 |
|---|---|---|
| small | 约 44 秒 | 约 9 分钟 |
| large-v3-turbo | 约 72–121 秒 | 约 15–25 分钟 |

turbo 的数字有一部分是在其他任务抢占 CPU 时测的，偏保守。

## 2. 硬件约束与配置档位

约束：开会用的电脑配置不高；用 CUDA 时显存占用不超过 3 GB。

### 2.1 设计原则

- **纯 CPU 必须是完整可用的路径**，不能把 GPU 当前提。会后离线处理，1 小时会议在 15–25 分钟内出结果是可以接受的。
- **GPU 上同一时刻只放一个模型**。转写完成后先释放 whisper 模型，再做分离；或者分离始终放在 CPU（ECAPA 模型很小，CPU 够用）。
- **自动选档加自动降级**：启动时探测显存，选不超过预算的档位；遇到显存不足时自动回退到 CPU int8 重试，而不是崩溃。
- 大模型在云端，不占本地显存。

### 2.2 建议档位

| 档位 | 自动选择条件 | 转写模型 | 计算类型 |
|---|---|---|---|
| CPU 省内存 | 总内存不足 15 GiB、可用内存不足 6 GiB，或无法探测 | small | int8 |
| CPU 标准 | 总内存至少 15 GiB、可用内存至少 6 GiB | large-v3-turbo | int8 |
| GPU 标准 | CUDA 运行库可加载，目标配置实测峰值不超过 3072 MiB，空闲显存额外留 256 MiB | large-v3-turbo | int8_float16 |

补充：

- GPU 档不要开批量推理，批量会成倍抬高显存。
- Windows 上 faster-whisper 的 CUDA 路径还依赖 CUDA 12 和 cuDNN 运行库，安装门槛不低，预检命令要能识别"有显卡但缺运行库"并给出提示。
- 录音期间不要同时跑转写，避免抢占 CPU 造成录音丢帧。

### A5. 预检命令 `doctor` — P0【读码】
- **问题**：`run` 模式下，Key 没配、模型没下载、依赖缺失、显存不够，都要等会议录完才暴露。

### B6. 设备切换处理 — P2【推断】

## C. 转写

### C5. Provider 能力声明 — P2【读码】
- **问题**：`pipeline.py:62` 用 `provider.name == "faster_whisper"` 判断是否本地。新增一个本地 ASR 就要改编排层。
- **思路**：在 `ASRProvider` 上加类属性，如 `needs_local_audio`、`provides_speakers`、`supports_progress`，编排层只看能力。
- **难度**：难度 2。

### C6. 云端转写的健壮性 — P2【读码】
- **问题**：`dashscope_asr.py` 轮询时不检查 HTTP 状态码，不检查子任务状态；要求音频有公网 URL，实际很难用。
- **思路**：补状态检查和错误信息；评估服务端的临时文件上传接口，免去用户自备 URL。
- **难度**：难度 5。

### C7. 评估其他识别引擎 — P2【推断，未测试】
- **问题**：whisper 对中英混杂术语的谐音错误是结构性的。
- **思路**：用基准集评估 SenseVoice、Paraformer 等中文优化模型（可通过 sherpa-onnx 以 ONNX 方式运行，不依赖 torch，CPU 友好，其中部分模型支持热词）。我没有测过它们在这类录音上的表现，是否值得替换要由指标决定。
- **难度**：难度 9。属于调研和实验设计。

## D. 术语表

实验结论：术语表只做"喂给识别模型"一层不够，需要三层配合（D1–D3 已完成，剩余纪要层与积累闭环如下）。

### D4. 纪要阶段：结合术语表纠错 — P1
- **思路**：把术语表和解释放进分段压缩和最终合成的提示词，明确要求"遇到与术语表读音相近的词，按术语表写法"。不增加调用次数，只多少量输入 token。术语表很大时只注入当前片段命中或疑似命中的词条。
- **难度**：难度 4。

### D5. 术语的积累与确认 — P2
- **思路**：
  - 每次转写后自动提取候选：高频英文词和缩略词、同一位置附近写法不一致的词、纪要模型标记的可疑词；
  - 新增 `glossary review` 命令，逐条接受、修改或忽略后才入库；
  - 用户手工改过的转写文本，与原文比对后自动生成"误听 → 标准写法"候选；
  - 绝不自动入库（实测教训见 1.1 节第 4 条）。
- **难度**：难度 5。

### D6. 基准集与评测脚本 — P0
- **已建立最小基准（2026-11-15）**。使用现有 5 分钟会议录音及人工校对的 `data/sessions/example/label.txt`。标注共有 14 段、5 个不同的说话人标签，后续评分以这份标注为准。
- **评测脚本**。`scripts/evaluate_transcript.py` 读取原始转写或分离后的 JSON，输出字符错误率、按次数统计的术语召回、说话人数和按时间计算的归属错误率。参考段终点取下一段起点，最后一段取录音结束。归属错误率按转写覆盖区间计算，另报告覆盖秒数。
- **首条基线**。本地 Whisper Small、CPU int8、关闭前文条件、使用默认标点提示设置。5 分钟录音的字符错误率为 21.45%（269 / 1254），D1 的 7 个指定术语在标注中有 11 次出现，按标准写法命中 0 次。指标保存在本地 `data/d6/sessions/small-cpu/asr_metrics.json`。
- **说话人基线**。首次实测发现 ECAPA 的输入维度回退问题，修复后用默认阈值 0.55、自动人数在 CPU 重跑。转写输出 45 个标签，人工标注为 5 个。转写覆盖 247.42 秒，按覆盖区间计算的归属错误率为 35.01%。修复前的降级状态与修复后的指标分别保存在同目录的 `diarization_before_fix.json` 与 `diarization_metrics.json`。[SpeechBrain ECAPA 模型](https://www.google.com/search?q=https://huggingface.co/speechbrain/spkrec-ecapa-voxceleb/tree/0f99f2d)
- **后续**。补两三段不同场景的录音，复测异常检测、模型档位和说话人分离。音频、标注和详细转写结果保存在 Git 忽略的本地数据目录。

## E. 说话人分离与识别

### E5. 换人边界偏差 — P2【读码】
- **问题**：相邻窗口重叠 0.75 秒，`align.py:18` 取第一个命中的片段，边界处总是偏向前一个说话人。
- **思路**：相邻不同说话人的片段，边界取两个窗口中心的中点，使片段互不重叠。
- **难度**：难度 5。

### E6. 重做聚类 — P1【实测】
- **问题**：见 1.3 节。给定正确人数 4 也只能分出两个大簇；阈值没有稳妥默认值。
- **思路**（按投入从小到大，用基准集逐步验证）：
  1. **改嵌入单元**：不用固定 1.5 秒滑窗，改为按转写句子（或合并后的 2–4 秒语音段）提嵌入，太短的段不参与聚类；
  2. **剔除异常点**：聚类后把总时长很短的小簇并入最近的大簇，再重新计数；
  3. **换聚类算法**：谱聚类加特征间隙自动估计人数，通常比固定阈值的层次聚类稳；
  4. **二次重分配**：得到簇中心后，所有段按与中心的相似度重新归属一遍；
  5. **评估成熟方案**：pyannote、sherpa-onnx 自带的分离流程、3D-Speaker 的 CAM++ 中文声纹模型。其中 sherpa-onnx 不依赖 torch，能省掉 2–3 GB 的安装体积，也更适合低配机器。这些方案我没有在该录音上测过。
- **硬件**：声纹模型放 CPU 即可，不占显存预算。
- **难度**：难度 9。算法选型加实验，是整个规划里最需要判断力的一项。

### E8. 声纹注册与跨会议识别 — P1（你提出的想法，建议纳入）

这个想法值得做，而且对例会场景，它比纯聚类更可靠：已知"谁可能在场"后，问题从"无监督聚类"变成"有参照的匹配"，1.3 节里阈值敏感、人数估不准的问题会大幅缓解。

**依赖**：E6（至少完成前两步）。

**参考方案**：

1. **存什么**
   - 位置：`data/speakers/voiceprints.json`（或每人一个文件），不进 git；
   - 每人保存：姓名、若干条"会话级中心向量"（192 维，已归一化）、每条对应的会话和有效语音时长、声纹模型名和版本、更新时间；
   - 保留多条而不是只存一个平均值，以适应同一个人在不同设备、不同状态下的音色差异；每人保留最近 5–10 条。

2. **注册**（会后执行）
   - 用户通过 `speakers rename` 给本次会议的说话人命名；
   - 系统取该说话人的窗口嵌入，筛掉质量差的（太短、能量低、离簇中心远、疑似多人重叠），对其余求平均得到本次的中心向量；
   - 有效语音不足一定时长（建议 20–30 秒）时不入库，只提示"样本不足"。

3. **识别**（下次会议）
   - 方式一（先做，简单）：照常聚类，然后把每个簇的中心与声纹库逐一算余弦相似度，用一对一最优匹配（匈牙利算法）分配姓名；相似度低于阈值的簇保持"说话人X"；
   - 方式二（后做，更稳）：把已注册的声纹当作"锚点"。先把每个语音段分给相似度最高且超过阈值的锚点，剩下的段再聚类，得到的新簇就是新面孔。这样人数和归属都由锚点主导；
   - 可以给会议配置"预期参会人名单"，只在名单内匹配，减少误认。

4. **置信度与确认**
   - 相似度落在灰色区间时，标成"张三？"，并在转写文件头部列出待确认项；
   - 用户确认或纠正后，本次的中心向量才并入声纹库。未确认的结果不更新声纹库，避免错误累积。

5. **阈值**
   - 不要写死经验值。用基准集和多次会议的数据统计"同一人"和"不同人"的相似度分布来定；
   - 注意通道差异：经过会议软件压缩的远端声音，与本地麦克风直录的声音，同一个人的嵌入也会有偏移。两种来源的声纹最好分开存。

6. **与双轨录音的配合**
   - 双轨录音启用时，麦克风轨直接就是"我"，本人的声纹可以自动注册，无需手工命名。

7. **隐私**
   - 声纹属于生物特征信息。只存本地；提供列出和删除某人声纹的命令；注册前在文档和命令提示里说明需征得本人同意；可选加密存储。

8. **模型绑定**
   - 换声纹模型后旧向量不可用，加载时校验模型名和版本，不匹配则提示重新注册。

- **难度**：难度 9（方案设计与方式二）；其中存储读写和命令行部分可拆给难度 5。

## F. 纪要生成

### F4. 分段方式 — P1【读码】
- **问题**：
  - `minutes.py:70` 硬切超长行后，后半段没有"说话人X:"前缀，归属丢失；
  - 同说话人合并没有长度上限，单人长发言必然触发硬切；
  - 各段之间没有重叠，跨段的讨论会断开。
- **思路**：合并时设单条上限；切分点优先选说话人轮次边界，其次选句末标点；硬切后的每一段都补上说话人前缀；相邻段保留一两句重叠，或把上一段的要点摘要作为下一段的上下文。
- **难度**：难度 5。

### F5. 分段结果缓存与并发 — P2【读码】
- **问题**：分段压缩串行执行；中途失败后，前面花的 token 全部作废。
- **思路**：按"片段内容 + 提示词 + 模型名"的哈希把每段结果缓存到会话目录，重跑时跳过已完成的；加小并发（2–4），遇到 429 自动降并发。
- **难度**：难度 5。

### F6. 失效的配置项 — P2【读码】
- **问题**：`summarizer.chars_per_token` 在配置里存在，但没有任何代码读取，估算系数是硬编码的 1.5。服务端不返回用量时，输入 token 被记为 0。
- **思路**：让估算真正读取该配置；输入和输出都做估算。
- **难度**：难度 1。

### F7. 纪要可溯源 — P1
- **问题**：纪要默认不带时间戳，结论和行动项无法跳回原文核对。
- **思路**：分段压缩时保留每条要点的起始时间；最终纪要在要点末尾附"[12:34]"形式的锚点，对应 `transcript.md` 里的位置。增加的 token 很少。
- **难度**：难度 5。

### F8. 纪要模板 — P2
- **思路**：把输出结构从代码常量改成可选模板（周会、评审、访谈、面试等），通过 `--template` 或配置选择；用户可以放自定义模板文件。
- **难度**：难度 4。

### F9. 纪要版本保留 — P2【读码】
- **问题**：每次重新生成都覆盖 `minutes.md`。
- **思路**：覆盖前把旧文件改名为带时间的备份；文件尾部记录模型名、模板、术语表版本。
- **难度**：难度 1。

## G. 工程质量

### G1. 配置校验 — P2【读码】
- **问题**：配置全程以 `dict` 传递，没有校验。拼错的键被静默忽略，类型错误到运行时才暴露。
- **思路**：改成 dataclass 或 pydantic 模型；未知键给出警告并提示最接近的正确键名；支持 `.env` 文件读取 API Key。
- **难度**：难度 5。

### G2. 日志 — P2【读码】
- **问题**：`print` 和未配置的 `logging` 混用，没有日志文件，出问题难以排查。
- **思路**：统一用 `logging`；控制台输出简洁信息，完整日志写入会话目录；加 `--verbose`。
- **难度**：难度 4。

### G3. 路径问题 — P2【读码】
- **问题**：配置文件和输出目录相对当前工作目录；声纹模型缓存目录相对源码目录，打包安装后会失效。
- **思路**：输出目录相对配置文件位置解析，或默认放用户目录；模型缓存统一放用户缓存目录，并可用环境变量覆盖。
- **难度**：难度 2。

### G4. 测试覆盖 — P2【实测 + 读码】
- **初次评估**：当时 13 项离线测试集中在纯函数。
- **当前进展**：已增加命令入口、会话匹配、防覆盖、电平与无数据告警、假设备/可控时钟/并发故障录音测试及独立 Windows 实机验收脚本；LLM 重试与截断路径已覆盖模拟 HTTP 响应。
- **仍需改进**：配置测试与用户本地配置的解耦，以及录音长时和多设备覆盖；LLM 的重试和截断已覆盖模拟响应，但未逐家服务实测。
- **后续思路**：保留 HTTP、会话及录音回归测试并扩充实机场景；配置测试改用内置默认配置和临时配置文件，而不是断言用户的仓库配置。
- **难度**：难度 5。

### G5. 文档与代码不一致 — P1【读码】
- **问题**：
  - `transcript.json` 里的"会议时间"取的是音频文件修改时间，对录音来说是结束时间，对外部文件则没有意义。
- **思路**：会议时间在录音开始时记录，外部音频允许用参数指定。
- **难度**：难度 1。

## H. 产品体验与远期

### H1. 合规提示 — P1
- **思路**：录音开始时打印一行提醒"请确认已告知参会人"；README 增加相应说明；声纹功能（E8）同理。
- **难度**：难度 1。

### H2. 会议历史与检索 — P2
- **思路**：新增 `list` 和 `search` 命令，列出历史会话（时间、时长、参会人、主题），按关键词搜索转写和纪要。
- **难度**：难度 5。

### H3. 导出 — P2
- **思路**：纪要导出为 Word、飞书或钉钉文档格式；行动项导出为表格。
- **难度**：难度 5。

### H4. 托盘或极简界面 — P3
- **思路**：系统托盘图标加"开始 / 结束"两个按钮，结束后自动转写和生成纪要；显示录音电平。面向不用命令行的同事。

### H5. 边录边转写 — P3
- **思路**：基于分段落盘，每段录完即转写，会后只需等最后一段和纪要；进一步可做滚动摘要。低配机器上要注意与录音争抢 CPU，建议仅在 GPU 档位或空闲核较多时开启。
- **难度**：难度 9。

## 4. 建议的实施顺序

按 2026-11-15 的进展更新。优先建立可复跑的评测基线，同时推进纪要改进和录音实机验收。下表的先后关系适用于同一条工作线。

| 顺序 | 内容 | 目标与范围 |
|---|---|---|
| 持续补充 | D6 基准集 | 用已有 5 分钟标注和首次跑分作为对照，先验证各项改动，再补不同场景的录音，支撑默认值选择。 |
| 说话人 | E5、E6 | 用标注基准分别评估换人边界与聚类，待分离质量稳定后再做 E8。 |
| 纪要 | F4 → F7 → F5 | F4 可立即开始，先稳住长转写的切分和说话人上下文，再沿同一分段传递可核对的时间戳。D4 在术语表和纪要分段就绪后接入，F5 待分段及提示词稳定后先做缓存，再评估并发。 |

同步验收与待办：

- **录音实机验收（长时/断电/双轨）**。有设备时并行推进。补至少一小时连续录音和有声强制中断后的分段恢复，有麦克风时核对双轨长时同步和恢复。若复现设备切换导致后半段失声，提前做 B6。缺少排查信息时先补 G2 的录音和恢复日志。扬声器外放串音的声学回声消除（AEC，参考 [WebRTC AEC 接口](https://webrtc.googlesource.com/src/+/refs/heads/main/api/audio/audio_processing.h)）暂缓，当前继续提示佩戴耳机。
- **小项随相关改动处理**。A5 基于现有 `doctor` 补仍缺的预检能力，并同步更新档位诊断建议。H1 的录音提醒可随验收改动加入。G5 优先处理会议时间来源和外部音频时间参数。
- **后续安排**。按使用场景排定其余 P2 项。C6 在云端转写成为常用路径时提前。C7、H4、H5 暂缓。

## 5. 仍待确认的事项

1. **CUDA 校准**：在目标机器上用代表性的长录音测量所选模型和解码配置的峰值，再配置 `asr.cuda_peak_mib`。
2. **WASAPI 环回在静音时的行为**：本机已验证无数据恢复与时间轴补齐，但仍需覆盖其他输出设备与长时间录音，不能据单机结果保证所有驱动行为一致。
3. **基准集扩充**：5 分钟示例已有带说话人的校对全文。后续补不同会议场景；需要精确衡量说话人边界时，再补细粒度的起止时间。
